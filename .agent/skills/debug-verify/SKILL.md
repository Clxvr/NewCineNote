# Стандарты проверки кода и отладки в CineNote

Данный документ определяет регламент верификации, поиска первопричин багов и обеспечения качества программного кода в проекте CineNote.

---

## 1. Обязательная компиляция и проверка сборки (dotnet build)

- **Строгое правило завершения задачи**:
  - Ни одна задача, фикс или рефакторинг не считаются завершенными без успешного прохождения команды `dotnet build`.
  - Запуск `dotnet build` обязателен сразу после редактирования любых файлов C# (`.cs`) или компонентов Blazor (`.razor`).

- **Политика нулевых ошибок (Zero Errors / Zero Warnings)**:
  - Любая ошибка компиляции должна быть устранена до передачи результата пользователю.
  - Предупреждения компилятора (`CS8618`, `CS8602`, `CS8604` о возможных null-ссылках, устаревших API или неиспользуемых переменных) должны анализироваться и своевременно исправляться, а не подавляться директивами `#pragma warning disable` без веской причины.

---

## 2. Принцип поиска первопричины (Root Cause Analysis)

- **Запрет временных костылей и фиктивных заглушек**:
  - Категорически запрещено маскировать баги:
    - Нельзя оборачивать сбоящий код в пустые блоки `try { ... } catch { /* ignore */ }`, скрывая исключения.
    - Нельзя подменять реальные данные из базы данных фейковыми мок-объектами в рабочих сервисах.
    - Нельзя убирать полезный функционал только потому, что в нем возникла ошибка.
  - Поиск первопричины строится на пошаговом анализе:
    1. Изучение точного стектрейса исключения (`NullReferenceException`, `InvalidOperationException`, `DbUpdateException` и др.).
    2. Локализация места сбоя (строка кода, состояние входных параметров, загрузка навигационных свойств EF Core).
    3. Исправление фундаментальной причины (например, добавление недостающего `.Include()`, проверка на `null` или обновление состояния жизненного цикла Blazor).

---

## 3. Отладка и диагностика взаимодействия Blazor с базой данных

- **Проверка состояния в базе данных**:
  - При возникновении проблем с сохранением или чтением данных проверять реальную схему таблиц и значения колонок в MS SQL Server / LocalDB.
  - Проверять соответствие имен колонок атрибутам `[Column("column_name")]` и внешних ключей `[ForeignKey]`.

- **Диагностика JavaScript Interop**:
  - При интеграции со сторонними библиотеками (Quill, анимации, Drag-and-Drop) проверять консоль браузера (`F12 -> Console`) на наличие JS-ошибок.
  - Использовать защищенные вызовы с перехватом `JSDisconnectedException` для предотвращения падений при разрыве SignalR-соединения.

---

## 4. Проверка граничных условий (Edge Cases)

Перед сдачей любого функционала необходимо убедиться в корректной работе следующих сценариев:
- **Пустые списки**: проект без единой сцены, фильм без персонажей, аккаунт без соавторов (проверка корректности отображения пустых состояний).
- **Экстремальные значения строк**: пустые строки, строки максимальной длины (логлайн > 250 символов), специальные символы (`<`, `>`, `&`, `"`, `'`).
- **Одновременные или повторные клики**: быстрая серия кликов по кнопкам сохранения не должна вызывать дублирование записей в базе данных.
- **Граничные права доступа**: открытие ссылки на проект неавторизованным пользователем или соавтором с правами «Читатель».
