# Стандарты аккуратных правок и рефакторинга в CineNote

Данный документ регламентирует правила безопасного внесения изменений в кодовую базу CineNote, направленные на предотвращение регрессий и сохранение стабильности работающего функционала.

---

## 1. Принцип минимального и точечного вмешательства (Surgical Edits)

- **Концентрация строго на поставленной задаче**:
  - Вносить изменения **только** в те строки, методы и файлы, которые непосредственно связаны с запросом пользователя.
  - Категорически запрещено попутно переписывать соседние классы, менять архитектуру работающих модулей, переименовывать публичные методы или реорганизовывать структуру каталогов «заодно».

- **Сохранение существующего контекста**:
  - Перед редактированием файла обязательно прочитать окружающий код, понять текущую логику и стиль именования.
  - Сохранять структуру отступов, соглашения по коду и уже настроенные зависимости.

---

## 2. Запрет на немотивированное изменение моделей и схемы БД

- **Неприкосновенность моделей сущностей**:
  - Запрещено удалять, переименовывать или менять типы существующих свойств в моделях (`MovieProject`, `Scene`, `Character`, `User`, `ProjectShare`), если об этом явно не просил пользователь.
  - Любое изменение структуры модели может сломать существующие миграции, сериализацию или запросы Entity Framework Core.
  - Если для задачи требуется новое поле или вспомогательная логика, предпочитать расширения (Extension Methods), вычисляемые свойства `[NotMapped]` или DTO-модели.

---

## 3. Защита от потери работающего функционала (Регрессии)

- **Сохранение функционала интерфейса**:
  - При стилизации карточек или компонентов нельзя случайно удалять скрытые обработчики событий (`@onclick:stopPropagation`, drag-and-drop события, валидаторы форм, привязки данных).
  - Если пользователь просит изменить одну деталь (например, убрать кнопку или поменять цвет бейджа), вся остальная функциональность карточки (раскрытие, перенос, нумерация, счетчики) обязана оставаться в полностью рабочем состоянии.

- **Обратная совместимость API и сервисов**:
  - При расширении методов сервисов добавлять опциональные параметры со значениями по умолчанию либо создавать перегрузки методов, чтобы не ломать существующие вызовы в других компонентах.

---

## 4. Контроль изменений через Git Diff

- **Самопроверка перед фиксацией**:
  - Перед коммитом всегда выполнять проверку списка измененных файлов и диффа (`git status` и `git diff`).
  - Убедиться, что в диффе отсутствуют:
    - Случайно задетые нерелевантные файлы;
    - Потерянные куски кода;
    - Случайные изменения форматирования (массовое переформатирование пробелов, ломающее историю git blame).
  - Только после подтверждения чистоты изменений и успешного билда (`dotnet build`) изменения фиксируются в Git с осмысленным сообщением.
